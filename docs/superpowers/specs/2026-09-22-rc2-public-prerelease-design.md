# v0.1.0-rc.2 Public Prerelease Design

## Status and decision

This document defines a narrow public `v0.1.0-rc.2` GitHub prerelease. It is
not a `v0.1.0` stable-release plan and does not weaken the existing stable
release Definition of Done.

The purpose is to let other developers inspect and try Commit CI Preflight
(CCP), especially maintainers of private repositories that pay for GitHub
Actions, while keeping claims, evidence, and operating boundaries honest.

## Audience and outcome

The release is for developers who want to run covered heavy CI work on a
controlled local machine, retain exact-commit evidence, and use a small
GitHub-side verification gate instead of repeating eligible hosted work.

Success means a new user can identify the problem, understand when savings are
real, download a bounded macOS arm64 prerelease artifact, verify its checksum,
read the limits, and choose a safe first evaluation. It does not mean that
every project, platform, or GitHub Actions workflow is supported.

## Release contents

The prerelease may contain only the following public, reviewable artifacts:

- exact source tag `v0.1.0-rc.2`;
- source archive generated by GitHub for that tag;
- unsigned macOS arm64 executable archive;
- SHA-256 checksum manifest binding every published asset;
- SPDX SBOM and third-party notices matching the exact release source;
- release notes, installation instructions, and rollback guidance;
- updated support matrix and economic-eligibility documentation.

The release must not publish a package registry artifact, installer, signing
identity, key, KMS configuration, Homebrew formula, Windows/Linux binary, or
automatic upgrade path.

## macOS-v5 change

`rc.2` communicates the installed macOS-v5 admission policy:

- heavy CCP commands remain serialized by one shared admission slot;
- admission still requires valid telemetry, at least 20% available memory, and
  at least 3 GiB reclaimable uncompressed memory;
- static swap occupancy alone is no longer a pre-start or immediate-stop veto;
- sustained converging pressure signals still stop work fail-closed;
- malformed, contradictory, unsupported, or unavailable telemetry still
  blocks execution.

This is an operational safety improvement, not a claim that any workload is
safe under arbitrary memory pressure.

## Economic claims

CCP may save GitHub Actions charges only when all of the following are true:

1. the repository is private or otherwise uses a billed runner SKU;
2. a local CCP workflow actually suppresses the covered hosted job;
3. the job topology, per-job rounding, allowance, rate, retained remote jobs,
   failed local attempts, and local operating costs have been recorded;
4. an exact-head receipt gate or equivalent verified mechanism preserves the
   required remote review boundary.

Public repositories using standard GitHub-hosted runners must remain on hosted
CI for ordinary pull requests: their standard runner minutes have no billed
price, so local substitution is not a monetary saving.

The public documentation keeps four quantities separate:

| Quantity | Meaning | Permitted public claim |
|---|---|---|
| Remote compute avoided | Hosted work not executed | Measured or bounded estimate |
| Included quota preserved | Avoided included minutes | Measured or bounded estimate |
| GitHub charges avoided | Avoided billable minutes times the observed SKU rate | Measured only for the documented billing phase |
| Net savings | Charges avoided minus electricity, hardware, maintenance, failures, and operator time | Not claimed until those costs are measured conservatively |

The release may cite the existing local-only evidence as examples, with their
limits:

- Matryca-Knowledge: 28 rounded Linux runner minutes, approximately `$0.168`,
  observed across 30 receipt-gate events during a billed phase. This is not a
  general monthly or net-savings claim.
- Matryca-Brain: approximately 635.1 runner minutes and `$3.81`, a bounded
  counterfactual estimate scaled from observed hosted validations. It is not
  an invoice total or independently certified net saving.

GitHub pricing, included quotas, and rounding rules can change. Every adopter
must remeasure current billing inputs before relying on any estimate.

## Time-to-feedback claims and evaluation

Cost and time are related but different. `rc.2` will explain the potential
time-to-feedback benefit without claiming a universal speed-up: a local machine
can avoid hosted queue time and may start a covered workload immediately, but
its hardware, current load, cache state, and network dependencies can also make
it slower.

Each published case study must report the following separately for the same
commit range and equivalent test scope:

| Measure | Definition | Use in a public claim |
|---|---|---|
| Hosted job duration | GitHub runner start to terminal job result | Remote execution baseline |
| Hosted queue delay | Workflow dispatch to runner start | PR feedback latency baseline |
| Hosted end-to-end feedback | Push or dispatch to required check terminal result | Reviewer-facing baseline |
| Local CCP execution | Guarded workload start to terminal result | Local execution observation |
| Local end-to-end feedback | Deliberate local start to independently verified result | Developer-facing observation |
| Local preparation overhead | Snapshot, dependency/cache preparation, evidence publication, and any manual work | Must be disclosed; it is not zero by default |

The evaluation protocol must use at least ten successful, comparable events
when historical evidence permits. It must state the machine, runner SKU,
repository visibility, test matrix, cache state, date range, median and range,
and exclusions. Failed, cancelled, retried, or non-equivalent events are
reported separately rather than discarded. If fewer than ten comparable events
exist, the result is labelled exploratory.

The release may say that CCP can reduce *waiting time* when measured local
end-to-end feedback is lower than the comparable hosted measure. It must not
equate faster feedback with billed savings, and it must not extrapolate one
machine's result to other hardware or repositories.

Release documentation will include a reproducible evaluation worksheet and
fixture-driven tests for its calculations: timestamp ordering, equivalence
guards, per-job billing rounding, median/range calculation, incomplete-data
rejection, and separate rendering of charges, quota, avoided compute, and
time-to-feedback. These tests validate the reporting method, not a future
user's actual saving.

## Evidence and acceptance gates

Before a release candidate can be proposed for publication, its exact source
must have:

- a clean selected Git commit and reproducible release metadata;
- passing deterministic format, lint, documentation, and test checks;
- a macOS arm64 archive built from the selected source and matched to its
  SHA-256 manifest;
- an SBOM and notices derived from the locked dependency set;
- a documented install and rollback smoke check on the claimed platform;
- passing fixture-driven checks for the published cost and time-to-feedback
  reporting calculations;
- release notes that distinguish source evidence, native platform evidence,
  hosted CI evidence, and unqualified surfaces.

The release manager must independently verify every final asset digest after
upload. A passing source suite does not prove an uploaded asset identity.

## Explicit non-claims

`v0.1.0-rc.2` does not claim:

- stable `v0.1.0` support or production enforcement approval;
- producer identity attestation, signing, or a trusted package channel;
- complete project `run` qualification on Linux or Windows;
- complete sandboxing of hostile project code;
- universal GitHub Actions compatibility;
- monetary savings for public standard hosted CI;
- net savings after local machine and operator costs.

## External authorization boundaries

The following are separate owner actions and must never be inferred from this
design:

- creating the tag;
- uploading or publishing GitHub release assets;
- editing GitHub release metadata;
- using signing identities or secrets;
- publishing a registry package, installer, formula, or announcement.

## Delivery sequence

1. Review and commit this design and a release implementation plan on an
   isolated branch.
2. Implement only the documentation, artifact, checksum, SBOM, and release
   metadata changes required by this scope.
3. Run the approved qualification commands against one exact candidate head.
4. Open and review a draft release PR; stop before any tag or publication.
5. Obtain separate exact authorization for final assets, tag, and GitHub
   prerelease publication.
