# ADR 0001: Rust for the production core

- Status: Accepted
- Date: 2026-08-08
- Decision owner: Marco Porcellato

## Context

Commit CI Preflight executes developer-controlled commands, handles paths and
processes, parses untrusted configuration and receipts, and must behave
consistently across macOS, Linux, and Windows. The core should be distributable
as a small native binary without requiring a language runtime.

## Decision

The production core and CLI will be written in stable Rust, beginning with the
2024 edition. The repository pins a development toolchain while declaring a
separate minimum supported Rust version when compatibility is actually tested.

Rust owns:

- configuration parsing and validation;
- execution-plan normalization;
- container-runtime process orchestration;
- timeout, cancellation, and stale-run controls;
- canonical receipt construction and verification;
- cache addressing, inventory, and safe cleanup;
- the CLI and machine-readable exit behavior.

Shell scripts may exist only as thin operator conveniences. They must not own
trust, receipt, policy, or orchestration semantics. A GitHub Action wrapper may
invoke the compiled verifier but must not reimplement it in JavaScript.

## Consequences

Benefits:

- one native binary with strong type and memory safety;
- explicit error handling around process and filesystem boundaries;
- deterministic serialization can be centralized in one library;
- good cross-compilation and static-analysis tooling;
- no Python, Node.js, or JVM runtime required by the core.

Costs:

- initial implementation is slower than a shell prototype;
- cross-platform process cancellation needs deliberate design and tests;
- dependency selection must remain conservative;
- contributors need a Rust toolchain.

## Rejected alternatives

- **Go:** operationally simple, but not selected because the owner explicitly
  chose Rust and values stronger low-level invariants for receipt and process
  boundaries.
- **Python:** excellent for prototyping, but adds runtime and environment
  variability to the artifact that is intended to verify environments.
- **Shell:** useful as an adapter, but unsuitable as the authoritative policy
  and canonicalization implementation.

## Guardrails

- No `unsafe` code without a dedicated ADR, safety proof, and focused tests.
- New dependencies require purpose, license, maintenance, and transitive-risk
  review.
- Receipt bytes are generated by one canonical implementation.
- Platform adapters cannot redefine policy semantics.
